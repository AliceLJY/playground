# 浮空之城 · 制作规格

体验：用手转动一座精细的云端袖珍城市，拨动昼夜、登上巡航飞艇，在静音的两三分钟里发现窗灯、空桥与瀑布。主美学为**感官、探索**；电脑鼠标双手或手机单手触屏，静音也完整。这是可反复探索的沙盘，没有输赢；首访 30 秒内可选择时间、地标或登艇，不以通关率验收。

## 视觉与构图

- 纯代码高密度体素，世界网格 0.22 单位；默认 C：象牙石墙 `#e8d5b1`、青铜绿屋顶 `#197d7e`、金色收边 `#d8a344`、蓝灰岩 `#5b6b79`、苔绿 `#779752`、暖窗 `#ffc17a`。均为 sRGB 输入，Three.js 线性照明后转 sRGB。
- 倒锥岩根、街巷城墙、抬升主殿三层；中心穹顶、四座带拱窗尖塔；四座小岛、桥、根须、晶石、瀑布、铜色飞艇。避免平滑原始体代替体素建筑。窗框、檐口、栏杆最细一格。
- hero：黄昏，固定种子 731，真实动画推进 12 秒；斜俯视约 24–33°，主岛主体占可用画面宽 45–78%，顶层与倒锥全部入画；光从画面左上来。wide：远景云海，主体宽 28–58%；night：深夜近景，暖窗清晰且不烧白。手机自动增加距离，主体留在上标题与下操控栏之间。
- 参考：给定《视频九案例-gemini整理》案例 1；给定九案例拼图的案例 1 截帧实际是终端，没有城堡可供逐像素对照。因此保留原拼图与文字来源说明，按“石材色差/体素构件/飞艇/光影”四项自审；不伪称有三机位原作图。三个自有固定机位均出图，后续可与 owner 的原作截帧并排。

## 性能与实现预算

目标桌面 Chromium 1440×900（硬件 GPU 目标稳定 30 fps），手机模拟 390×664（目标 30 fps；真机待测）。可见页主动封顶 30 fps；减少持续 GPU 占用，不声称据此证明温度。设备 DPR 桌面 ≤1.5、手机 ≤1.25（窄屏或粗指针识别，横屏仍按手机封顶）；自适应三档比例 1 / .82 / .65，连续 45 个超 38 ms 的渲染样本降档，连续 300 个低于 24 ms 的样本升档，切档后 90 帧冷却。重效果为生成时顶点 AO，无全屏重着色器、无实时 SSAO。

总体素预算 200,000–800,000（含内部逻辑体素；实测城市 463,099 + 飞艇 15,371 + 旗帜 84 = 478,554），相邻面剔除，外露面合并为按材质的少量网格；≤150 draw calls（含阴影更新），≤1,500,000 实际提交三角形。阴影 2048² PCF，静态场景首次与时段变化后更新，拖动时最多 2 Hz；飞艇不投实时阴影。全场仅一盏投影方向光、一盏半球光、两盏不投影点光，夜灯共用发光网格。水花/雾/烟 ≤420 粒子（实际 348）；另有静态星点 500 个；云 ≤100 个合并/实例块或解析点精灵。每帧不新建几何、不创建临时 Three 对象。不可见、后台、离开视口时取消 rAF；可见恢复重新请求一帧。

## 第三轮：配色检查（A11）

反馈原话：「另外两个的配色不太行哈哈哈」。本轮只调整配色、照明、远雾与云的明暗，保持结构、机位、时刻和交互。三套完整配色的 sRGB HEX、四时段主光近似色温 / 强度、半球光、线性雾距离与材质微调以 `src/palettes.js` 为执行数据；`?palette=a|b|c` 仅供对照，不加界面按钮。天空由顶部 / 48% / 82% / 底部四节点渐变，四时段间在 Three 线性颜色空间连续插值。

采样：真实 Chrome GPU，1440×900 CSS、DPR 1、种子 731、动画 12 秒；hero/wide 为黄昏，night 为深夜。相同正常渲染路径，无额外画质锁。`tools/palette-render.cjs` 采集 WebGL 原帧（不含 HUD 与 CSS 遮罩），同机位另取城市+背景、仅背景、纯天空、白色城市轮廓。后三次隐藏其他动态前景，城市遮罩向内收 1 像素；只在城市实覆像素测主体，在背景与纯天空差 ≤3/255、且不覆城市的像素测天空。云海仍计入全帧亮度与灰色比例。禁止用整块矩形替代主体。

亮度 Y′ = (.2126R + .7152G + .0722B)/255，**sRGB 显示亮度代理，非物理线性光亮度**。色相用 HSV 的饱和度加权圆均值（S≥.01、V≥.05）再取最短角距；另记录圆均值集中度，低饱和度的色相只作辅助，不能单独证明冷暖。灰色定义 HSV S<.12；暗部也计入，不排除难看的区域。每张实际采到城市 >50,000、天空 >500,000 像素，否则失败。

| 机位 | p5–p95 跨度 ≥ | 城市/天空平均亮度差 ≥ | 平均色相差 ≥ | 灰色比例 ≤ |
|---|---:|---:|---:|---:|
| hero | .50 | .12 | 45° | 35% |
| wide | .45 | .10 | 45° | 35% |
| night | .34 | .06 | 25° | 12% |

阈值理由：原版 hero/wide 跨度 .368/.194、灰色 87%/93%，需要恢复至少半个显示亮度量级的分层，不能只给灰背景染一点色；wide 的主体较小，跨度放宽 .05。主体均亮度与天空至少分开 .10–.12，避免同一中灰，同时不强迫夜景把全城照亮；夜间允许 .06 与 25°，由暖窗、暗岩、冷夜空共同建立层次。灰色上限给象牙墙与白云留出面积，夜间则应保持有色的蓝黑。夜间原版跨度 .279 也须失败。允许采样差 ±.003 作为测量解释，不在断言里偷偷放宽阈值。

运行 `node --test tests/palette.browser.cjs` 重新渲染并断言；`SKY_PALETTE_BASE=file://…/shots/r3-baseline.html SKY_PALETTE_OUT=shots/r3-old-test node --test tests/palette.browser.cjs` 在旧配色上运行相同检查，应变红。旧快照仅加入采样钩子，配色、雾、机位与材质未改，原始未加钩子版本另存 `shots/r3-original.html`。

## 第四轮：天空（A12，取代第三轮的大气配色）

反馈原话「天空颜色不好看，更土了～咋回事」。保留 C 的城市、岩体、屋顶、全部光源与材质参数，只重做天空、云与雾。移除 A/B 对照方案，旧参数回退到 C。

天空节点从上到下固定为 0 / .48 / .72 / .84 / .94 / 1。所有空间渐变与天空时段过渡均在 OKLCH 中取最短色相弧插值，越出 sRGB 色域时保持 L、h 缩减 C。1×2048 纹理按邻近采样，避免纹理过滤再引入 RGB 混色。黄昏天顶 #1F4FA8，中部 #4D8FE0，经明亮蓝紫色抵达仅在低位出现的 #FFC796 与 #FFB38A。正午从 #2F78D8 到 #CDE6FA，始终为蓝色。深夜从 #0B1530 到 #1E2E58。输入均为 sRGB HEX，插值使用 D65 OKLCH。

云受光面以 #FFF2DE 为暖白，阴面以 #A8B4D6 为淡蓝紫，使用显示色着色，云层使用独立显示色路径。下缘 CSS 蓝黑遮罩去掉，避免再次把暖天空压成褐色；底部文字补阴影以适应更亮的背景。深夜另用冷月光。远雾与瀑布水雾都使用当时 .94 节点的地平线色，沿用原雾距离。

真实 Chrome / GPU、1440×900、DPR 1。复用 capturePalette 的独立天空渲染，隐藏所有场景物体，每个像素都属于天空，再把真实 GPU 天空图放回原 CSS 遮罩下，由 Chrome 截取最终显示像素，逐行平均全部 1440 个像素，900 行无遗漏。默认入口保持无参数、正常自动环绕与自适应，页面时钟推进 12 秒。hero/wide/night 为原固定机位，种子 731、动画 12 秒。开发注入开关仅暴露原诊断钩子。只关闭加载遮罩的 CSS 过渡，天空和实际渲染路径不变。

## 第五轮修订：天空与云（2026-11-11，以本节为准，第三、四轮的天空与云描述作废）

反馈原话：第四轮上线后「还是土，天空蓝色怎么这么不高级」。第四轮按「每一行饱和度都要够」做，得到的是高纯度正蓝接粉紫再接蜜桃的彩虹渐变，加上一团团虚焦光斑似的云——饱和不等于好看，那条检查本身定错了方向。本轮改三件事：

- **天空是一块克制的背景板**：同一时段里只走「深蓝 → 钢蓝 → 淡蓝雾 → 奶油 → 杏色」一条线，蓝的 OKLCH 彩度不超过 .125；冷暖交界落在高亮度的淡色上（亮的中性读作光晕，暗的中性才是脏）。纵向渐变与时段过渡都在 OKLab 里走直线，不再走色相弧（弧会绕到粉或绿）。
- **云换成体素云**：平底、顶面按高度场一级级堆起的小方柱，约 4,550 根、一次实例化绘制，和城的体素语言一致。受光只按面的朝向分三档（顶面亮、向阳侧暖、背阳侧与底冷），远处的云不透明地化进它背后那一行背景色（片元里按屏幕行取同一张天空渐变），不做半透明混合，也不用雾色，远云不会变成一块色片。原来 86 个柔边云精灵删除，瀑布水雾的 80 个点保留。
- **黄昏到深夜之间加「余晖」关键帧（滑块 2.5，约 21:00）**：暖色地平线先暗成余烬红、上方转靛紫，再入夜；直接从杏色混到藏青会经过灰褐。时段标签在 2.2–2.8 之间显示「余晖」。
